> เอกสารนี้สรุปจากบทสนทนาวางแผน ใช้เป็นข้อมูลอ้างอิงคู่กับ docs/CHANGELOG.md / CLAUDE.md

> สำหรับรายละเอียดที่ต่างจากแผนเดิม, บั๊กที่เจอ, และสิ่งที่ยังไม่ได้ทำ

## 1. ปัญหาตั้งต้น (สรุปจากการวิเคราะห์)

กระทู้ (Thread) กับ Event เป็นคนละระบบที่ไม่เชื่อมกัน ทำให้เกิดปัญหาลูกโซ่:
- กระทู้ไม่รู้ว่าตัวเองผูกกับ Event ไหน / เงื่อนไขจบคืออะไร
- กระทู้ปิดเองไม่ได้ (Flash Event ต้องรอแอดมินปิดมือ)
- ปิดแล้วไม่รู้ว่าใครมีสิทธิ์ได้ reward → แอดมินไล่หาเอง แจกทีละคน
- หลังบ้านไม่มีข้อมูลสรุป/สถิติ เพราะไม่เคยถูกออกแบบให้เก็บตั้งแต่ต้น

**หลักการแก้:** ต้องสร้างโครงสร้างข้อมูลที่ผูก Thread ↔ Event ก่อน ทุกอย่างอื่น (UI, Dashboard, Stats) ต่อยอดจากตรงนี้ทั้งหมด

---

## 2. การตัดสินใจที่ยืนยันแล้ว (จากพี่ Kqicc)

| หัวข้อ | การตัดสินใจ |
|---|---|
| ความคืบหน้า reward | **เปิดเผย** ให้ผู้เล่นเห็น (ไม่ปิดบังเป็นเซอร์ไพรส์) |
| การแยกประเภทกระทู้ | ใช้ **ระบบ Tag ที่มีอยู่แล้ว** (color-coded) แทนการสร้างระบบใหม่ |
| หน้าจอควบคุมแอดมิน | เป็น **Dashboard หลังบ้าน** แยกต่างหาก |
| สถิติ (Stats) | ต้องการเก็บ แต่ปัจจุบันไม่มีเพราะ UX/โครงสร้างไม่เอื้อ — ยอมรับว่าอาจต้องเขียนใหม่บางส่วน |

---

## 3. แนวคิดหลัก: "Event Thread Template"

แทนที่แอดมินจะสร้างกระทู้แบบเดียวกับผู้เล่นทั่วไป ให้มีโหมด **สร้างกระทู้แบบ Event** ที่เลือก Template ได้ทันที:

```
แอดมินกด "สร้างกระทู้ Event" 
   ↓
เลือกประเภท Event (Flash / Location / Story Arc / Crisis)
   → ระบบดึงค่าเริ่มต้นที่เหมาะกับประเภทนั้นมาให้ (เวลาปิด, รูปแบบเงื่อนไข)
   ↓
ตั้งเงื่อนไข reward (เช่น ครบ 5 โพสต์ / อยู่จนจบ)
   ↓
ระบบ auto-tag กระทู้ด้วย Tag สีที่ตรงกับประเภท Event นั้น
   ↓
กระทู้ถูกสร้าง พร้อมผูก event_id ในตัว
```

**ทำไม Template ช่วยลดงานแอดมิน:** ไม่ต้องตั้งค่าทุกอย่างเองทุกครั้ง แค่เลือกประเภทแล้วระบบเติมให้ ตรงกับหลักที่พี่วางไว้ (ลดภาระงานแอดมิน)

---

## 4. การใช้ระบบ Tag ที่มีอยู่ (ไม่สร้างใหม่)

เสนอ mapping สี Tag ต่อประเภทกระทู้ — ใช้ตาม 4 ประเภท Event ที่มีอยู่แล้ว บวกกระทู้ RP ทั่วไป:

| ประเภทกระทู้ | ใช้ Tag สี (ตัวอย่าง) | ความหมายที่ผู้เล่นเห็น |
|---|---|---|
| RP ทั่วไป (ไม่มี reward ผูก) | สีเทา/กลาง | เล่นอิสระ ไม่มีเงื่อนไข |
| Flash Event | สีแดง/ส้ม (เร่งด่วน) | มีเวลาจำกัด 2–6 ชม. |
| Location Event | สีฟ้า/เขียว | เปิดยาว 1–2 สัปดาห์ |
| Story Arc | สีทอง/ม่วง (สำคัญ) | เปลี่ยน canon เกม |
| Crisis | สีดำ/แดงเข้ม | ไม่ประกาศล่วงหน้า 24–48 ชม. |

*(สีเป็นตัวอย่าง พี่เลือกจริงตามธีม Vaelthorn ได้ — สำคัญคือ 1 ประเภท = 1 สีตายตัว ผู้เล่นจำได้โดยไม่ต้องอ่านคำอธิบาย)*

**สิ่งที่ต้องเช็คก่อน:** ระบบ Tag ปัจจุบันรองรับการ "auto-apply" ตอนสร้างกระทู้ไหม หรือต้องแอดมินเลือกเองทุกครั้ง — ถ้ายังไม่รองรับ auto นี่คืองานเพิ่มเล็กๆ ในเฟส 1

---

## 5. ประสบการณ์ผู้เล่น (Player-facing)

**เห็นตั้งแต่แรก (ในลิสต์กระทู้ หรือหัวกระทู้):**
- Tag สีบอกประเภททันที
- ถ้าเป็น Event: แสดงเงื่อนไข reward แบบเปิดเผย (เช่น "โพสต์ครบ 5 ครั้งเพื่อรับรางวัล")
- ถ้าเป็น Flash: แสดงเวลานับถอยหลัง

**ระหว่างเล่น:**
- แสดงความคืบหน้าของตัวเอง (เช่น "3/5 โพสต์")

**ตอนกระทู้ปิด:**
- แจ้งผลทันที (ได้ reward หรือไม่ได้ เพราะอะไร) — ไม่ต้องให้ผู้เล่นไปเดาหรือถามแอดมินเอง

---

## 6. Dashboard หลังบ้าน (Admin-facing)

หน้าจอเดียวที่แอดมินเห็นภาพรวมทุก Event ที่กำลังทำงาน แทนการไล่เปิดทีละกระทู้:

- รายการ Event ที่เปิดอยู่ตอนนี้ + ประเภท + เวลาที่เหลือ (ถ้ามี)
- ต่อ 1 Event: จำนวนผู้เข้าร่วม, ใครครบเงื่อนไขแล้วบ้าง
- ปุ่ม "ปิด Event + แจก Reward" กดครั้งเดียว → เห็นสรุปก่อนยืนยัน

---

## 7. ระบบ Stats (ส่วนที่ยังไม่มีเลยตอนนี้)

พี่ระบุว่าอยากเก็บสถิติ แต่โครงสร้างปัจจุบันไม่เอื้อ เพราะไม่เคยมีจุดที่บันทึก "การเข้าร่วม Event" เป็นข้อมูลก้อนเดียว (ตอนนี้กระจัดกระจายอยู่ในโพสต์แต่ละอัน)

**สิ่งที่ควรเก็บ (เสนอเบื้องต้น เพื่อคุยต่อ):**
- จำนวนผู้เข้าร่วมต่อ Event / ต่อประเภท Event
- อัตราผู้เล่นที่เข้าร่วมแล้วได้ reward vs ไม่ได้ (ดู drop-off)
- ความถี่ Event แต่ละประเภทที่เปิด (ใช้วางแผน content ต่อได้)

**ข้อควรระวัง:** นี่คืองานที่ "เขียนใหม่" ตามที่พี่พูดจริง เพราะต้องมีตารางข้อมูลใหม่ (ไม่ใช่แค่ UI) — ควรทำเป็นเฟสท้ายสุด ต่อยอดจากตอนที่ Thread↔Event เชื่อมกันแล้ว (เฟส 1) เพราะ Stats ที่แม่นยำต้องพึ่งข้อมูลตรงนั้นอยู่ดี

---

## 8. ลำดับการสร้าง (แนะนำ เพื่อกันปัญหา scope creep)

| เฟส | สร้างอะไร | Deliverable ที่ทดสอบได้ |
|---|---|---|
| 1 | ผูก Thread ↔ Event ในฐานข้อมูล + auto-tag ตอนสร้าง | สร้างกระทู้ Event แล้วเห็น Tag สีถูกต้องทันที |
| 2 | หน้าสร้างกระทู้แบบ Template สำหรับแอดมิน | แอดมินเลือกประเภท Event → ฟอร์มเปลี่ยนตาม |
| 3 | UI ฝั่งผู้เล่น (progress, เงื่อนไข, แจ้งผลตอนปิด) | ผู้เล่นเห็นความคืบหน้าจริงระหว่างเล่น |
| 4 | Dashboard แอดมิน + ปุ่มปิด Event ทีเดียว | แอดมินปิด Event แล้วแจก reward ได้ในคลิกเดียว |
| 5 | ระบบ Stats | มีตัวเลขสรุปให้ดูหลัง Event จบ |

**เหตุผลของลำดับนี้:** แต่ละเฟสทดสอบได้จริงก่อนไปเฟสถัดไป ไม่ต้องรอสร้างครบทุกอย่างถึงจะเห็นผล และป้องกัน scope บานปลายเหมือนที่เคยเกิดขึ้นมาก่อน

## 9. สิ่งที่ต้องเช็คข้อเท็จจริงก่อนเริ่มเฟส 1

- ระบบ Tag ปัจจุบันรองรับ auto-apply ตอน create หรือไม่
- Thread model ตอนนี้มี field ที่ผูกกับ Event ได้เลยไหม หรือต้องสร้างใหม่ทั้งหมด
- หน้าสร้างกระทู้ปัจจุบัน แยก role แอดมิน/ผู้เล่นได้อยู่แล้วหรือยัง (มี permission check ระดับนี้ไหม)

## 10. สถานะจริงหลังทำเสร็จ (2026-08-02)

ทำครบทั้ง 5 เฟสแล้ว — commits `b65a49a` → `8328e3c` (main) เทสต์อัตโนมัติ 31/31 ผ่าน
(182 assertions, `tests/Feature/EventThreadIntegrationTest.php` +
`EventCloseActionTest.php` + `EventStatsTest.php` + `NotificationUrlTest.php`)

### สิ่งที่ต่างจากแผนเดิม (ของจริงไม่ตรงกับที่แผนสมมติไว้ตอนวางแผน)

1. **ไม่มี "N โพสต์ = ได้ reward" threshold เลย** — ระบบแจก reward ทันทีที่โพสต์แรก
   ในกระทู้ที่ผูก Event ได้รับอนุมัติ (dedup ผ่าน `reward_logs`, ดู
   `LevelingService::distributeEventRewards()`) เฟส 3 เลยแสดงสถานะ "ได้รับแล้ว/
   ยังไม่ได้รับ" แบบตรงกับของจริง แทนที่จะทำ progress bar "3/5 โพสต์" ที่ไม่มี
   backing logic รองรับจริง
2. **เฟส 4 ไม่มีปุ่ม "แจก Reward"** เพราะเฟส 1 แจกอัตโนมัติไปแล้วตั้งแต่ทีแรก — ปุ่ม
   "ปิด Event" ในเฟส 4 จึงโฟกัสที่ **bulk-lock กระทู้ที่ผูกอยู่ทั้งหมดในคลิกเดียว**
   (ปัญหาที่ยังไม่เคยถูกแก้จริง) พร้อม modal สรุปยอดก่อนยืนยันตามที่แผนต้องการ
3. **เฟส 5 ไม่ต้องสร้างตารางใหม่เลย** ตรงข้ามกับที่แผนข้อ 7 คาดไว้ว่าต้อง "เขียนใหม่"
   — เพราะ `event_participants` + `reward_logs` จากเฟส 1 มีข้อมูลครบพอสำหรับสถิติ
   ที่ต้องการ (ผู้เข้าร่วม, อัตราได้ reward) อยู่แล้ว เพิ่มแค่ 2 คอลัมน์ในตาราง
   EventResource ที่มีอยู่เดิม

### งานพลอยได้ (นอกแผน แต่แก้ไประหว่างทาง)

- Auto-approve กระทู้เมื่อแอดมิน approve โพสต์แรก (เดิมต้องกด approve 2 ที่แยกกัน)
- Notification แจ้งผู้เล่นเมื่อกระทู้ถูก reject/request_edit (เดิมไม่มีเลย)
- ข้อความเตือนผู้เล่นเมื่อโซนที่โพสต์จะไม่ได้ EXP (ไม่ผูก Event + require_approval)
- ทั้ง 3 ข้อนี้ตรงกับบั๊กที่เคยบันทึกไว้ใน `docs/audits/2026-07-29-qa-audit.md` (รายการ #4, #6, #8) — ดูไฟล์นั้น
  สำหรับรายละเอียด ตอนนี้ resolved แล้ว

### ยังไม่ได้ทำ (นอกขอบเขต 5 เฟสนี้)

- ทดสอบผ่านเบราว์เซอร์จริงด้วยตา (มีแต่ automated test + manual E2E ผ่าน tinker)
- `event_id` validation ตอนสร้างกระทู้ไม่เช็คว่า Event ยัง `status=active` ณ เวลา submit
  (race condition เล็กน้อย ความเสี่ยงต่ำมากที่ scale ปัจจุบัน)
- `ThreadController::moderate()`'s action `lock` (คนละอันกับ `closeEvent`) ไม่เช็ค
  status ก่อนล็อคเหมือนกัน — เป็นโค้ดเดิมของระบบ ไม่เกี่ยวกับ 5 เฟสนี้ ไม่ได้แก้
